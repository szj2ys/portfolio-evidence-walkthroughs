The walkthrough task

A design portfolio often shows a polished final screen but leaves the interviewer unable to see what changed or why. This fictional exercise follows a reservation form for a community studio. The artifact packet contains a before layout, a revised layout, and a review log. Your job is to explain a specific interaction problem and the boundaries of the evidence. The revision is a design proposal, not proof that people completed reservations faster. You can give a useful walkthrough before a release, provided you are clear about which checks happened and which are still planned.

The fictional artifact packet

All screens and review comments are invented for this exercise. The original form uses a generic Continue action, clears entries after a validation failure, and gives no field-specific guidance. The revised sketch names the action, keeps entered values, and connects an error to the affected field. These are written interaction requirements, not a screenshot of a functioning application. The packet deliberately includes an untested item so the speaker must distinguish design intent from observed behaviour.

Personal contribution boundaries

The fictional candidate identified the unclear error state, drew U2, and wrote the interaction requirements. A product reviewer clarified that the next step is a review page, not a final booking. A developer commented on feasibility. The candidate did not implement the form, run a participant study, or approve an accessibility audit. Describe these distinct contributions rather than saying “I redesigned and validated the booking flow.” The strongest supported claim is that the proposed state now specifies recovery behaviour that U1 omitted.

A two-minute walkthrough

The intervals below total 120 seconds. Point to an artifact as you speak; the outline is a rehearsal guide, not a script to memorise or a claim that the fictional experience is yours.

  1. 0–15 seconds · Define the task

    “A visitor is entering a reservation. This packet focuses on recovering from an invalid time range.” Keep the scope smaller than the whole booking journey.

  2. 15–40 seconds · Show the original failure

    Point to the empty fields and generic message in U1. Explain what information the visitor would need to enter again and what the message fails to identify.

  3. 40–75 seconds · Walk through the revised state

    Use U2 to show retained values, the End-field message, and the named next action. Describe what the interface should do after correction, without pretending the sketch is live.

  4. 75–100 seconds · Identify the evidence and collaborators

    Read the status column in U3. Credit the product reviewer’s next-step clarification and the developer’s feasibility input.

  5. 100–120 seconds · State the next verification

    “I would test the implemented recovery with keyboard interaction and a realistic task. This packet does not yet contain those results.”

Skeptical follow-ups and reasoned answers

How do you know the new version is easier to use?

The packet supports a rationale: U2 retains information and identifies the field involved. It contains no task-performance evidence. I would describe the expected benefit as a hypothesis, then test the implemented interaction rather than report an invented usability improvement.

Why change the button text as well as the error?

The product reviewer clarified that pressing the button opens a review step. “Review reservation” expresses that intended action. It is a separate clarity change, so a later test should not attribute every observed difference solely to the error message.

Is the revised form accessible?

The sketch specifies a field association and focus behaviour, but that does not verify an implementation. Keyboard operation, assistive-technology output, contrast, and other relevant behaviour would need actual checks. I would not turn a design annotation into an audit claim.

What did the developer contribute?

The developer commented on preserving entered values and the feasibility of the recovery state. The candidate owns the proposed interaction and documentation in this packet, while implementation remains uncompleted. That distinction also explains why the status table contains planned checks.

Try the exercise, then adapt it honestly

Cover U2 and explain the failure using U1 alone. Then reveal U2 and ask a partner to name which requirement addresses each failure. If they cannot connect a change to a problem, clarify the rationale or remove the unsupported claim. For your own portfolio, include an error or empty state alongside the attractive default screen. Write an evidence label next to every claim: design intention, review agreement, implemented check, or observed participant result. Do not silently move a claim from one category to another during rehearsal.

What this packet cannot establish

The layout is a text sketch, not production UI. It does not cover availability, overlapping reservations, time zones, cancellation, server errors, or complete accessibility behaviour. The examples do not establish that a community studio needs this product. Their purpose is to practise discussing a bounded revision and its verification status. A public portfolio should respect the ownership of any real designs or research; this fictional packet can be reused as an exercise without implying that you shipped the underlying service.
