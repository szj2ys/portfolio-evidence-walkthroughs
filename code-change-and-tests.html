The walkthrough task

A code portfolio becomes easier to discuss when the listener can inspect one behaviour rather than a large repository tour. This fictional packet concerns a ticket-import helper that removes blank identifiers and duplicate identifiers within one input batch. The exercise is to explain the bug, the chosen contract, and the limits of the evidence without claiming ownership of an entire import system. You do not need to memorise the implementation. You need to connect a specific input, a specific output, and the part of the change you can honestly explain. In your own portfolio, use only code you are authorised to disclose.

The fictional artifact packet

All code, review notes, identifiers, and test descriptions here are fictional teaching material. The old helper trimmed blanks but retained duplicates. The agreed contract is: accept a list of strings, trim surrounding whitespace, omit blank values, preserve the first occurrence of each remaining identifier, and keep letter case significant. That is a local import rule, not a universal rule for identifiers. Packet C1 is the change; C2 contains executable examples; C3 is a review note.

C1 · Before and after

Before:
return [value.strip() for value in raw_ids
        if value.strip()]

After:
def ticket_ids(raw_ids):
    seen = set()
    ordered = []
    for raw in raw_ids:
        key = raw.strip()
        if key and key not in seen:
            seen.add(key)
            ordered.append(key)
    return ordered

Personal contribution boundaries

In the fictional role, you wrote the helper revision and the cases in C2, and added a check that the original list remains unchanged. A reviewer identified the ordering requirement in C3. Another engineer owns parsing uploaded files and writing accepted records to the database. State those boundaries before using “I fixed the importer.” The packet supports a claim about one helper’s behaviour, not deployment, throughput, duplicate prevention across different files, or production reliability. A code excerpt also does not prove authorship on its own; an authorised work history or review trail would be a separate part of a real portfolio.

A two-minute walkthrough

The intervals below total 120 seconds. Point to an artifact as you speak; the outline is a rehearsal guide, not a script to memorise or a claim that the fictional experience is yours.

  1. 0–15 seconds · Name the narrow problem

    “This helper kept repeated ticket IDs inside one batch. My change addresses that local behaviour.” Point to C2a, where the duplicate is visible.

  2. 15–40 seconds · Show the old behaviour

    Explain why trimming blanks alone leaves two copies of A-7. Keep the distinction between whitespace cleanup and duplicate removal clear.

  3. 40–75 seconds · Explain the change

    Point to the seen set and ordered list in C1. Explain their jobs in ordinary words: remember what appeared, and retain the first-seen sequence.

  4. 75–105 seconds · Use the tests as evidence

    Walk through C2a and C2b, then name the case-sensitive boundary in C2c. Mention the separate unchanged-input check without reading every assertion.

  5. 105–120 seconds · State the limit and handoff

    “These cases check the helper. They do not prove database-level duplicate handling. That belongs to the integration work owned by another engineer.”

Skeptical follow-ups and reasoned answers

Why not return a set directly?

C3 says the preview depends on first-seen order. C2b makes that requirement visible: B-2 should remain before A-7. The extra ordered list preserves that sequence. This answers the documented contract; it does not claim that every caller needs stable ordering.

Does this prevent every duplicate ticket?

No. C1 starts with an empty seen set on each call, so it only removes duplicates within that input list. A second file can contain the same ID. Database constraints or an integration check would require their own evidence and are outside this packet.

What happens if an input item is not a string?

The declared helper contract accepts strings. The excerpt does not validate arbitrary objects. In a real system I would identify where that contract is enforced and add a boundary test there. I would not describe these four cases as complete input validation.

Which part was your decision, and which came from review?

The fictional candidate chose the helper change and wrote the examples. The reviewer supplied the ordering concern in C3. Crediting that contribution explains why C2b exists; claiming sole design ownership would erase a meaningful part of the work.

Try the exercise, then adapt it honestly

Cover the proposed answers and ask a partner to select one test row. Explain how the code produces that output, then ask the partner which larger claim the row cannot support. For your own portfolio, select one authorised diff and one meaningful test that would fail without the change. Annotate the failing behaviour, your contribution, and the reviewer’s contribution. Avoid filling the page with green test counts that do not explain the behaviour. A listener should be able to identify the repaired defect before you show a repository tree.

What this packet cannot establish

This is a small in-memory example with no file parser, concurrency, database, performance benchmark, or production rollout. The included cases are deliberately narrow. Passing them does not show that the surrounding product is safe to deploy or that a real user experienced an improvement. Keep that limitation in the spoken walkthrough. If you cannot share real code, an authorised simplified reproduction can demonstrate reasoning, but label it as a reproduction rather than presenting it as the actual production change.
